# `--no-mmap` 和 `--mlock` 详解

[English](no-mmap-and-mlock.md) | [简体中文](no-mmap-and-mlock.zh-CN.md)

结合 llama.cpp 官方文档和社区实践，这两个参数都与**内存管理**相关，但作用对象和机制完全不同。

---

## 核心定义

| 参数 | 官方说明 | 通俗解释 |
| ---------------- | --------------------------------------------------------------- | ---------------------------------------------------------------- |
| **`--no-mmap`** | 禁用内存映射（memory-mmap），强制将整个模型加载到 RAM 中 | **"直接加载"**：模型文件被一次性读入内存，不再依赖磁盘文件的映射 |
| **`--mlock`** | 强制系统将模型锁定在 RAM 中，防止操作系统将其换出（swap）或压缩 | **"锁在内存"**：告诉 OS "这部分内存不准动"，防止被交换到磁盘 |

默认情况下，llama.cpp 启用 `--mmap`（内存映射）且不启用 `--mlock`（不锁定）。

---

## `--no-mmap` 详解

### 什么是 mmap？

内存映射是一种操作系统机制：**模型文件并不加载到内存，而是建立一个"映射关系"**。当程序需要某块模型权重时，OS 自动从磁盘按需读取，就像访问内存一样。这有两个好处：

- **加载极快**：启动时不需要把整个模型读入内存
- **不耗 RAM**：OS 的页面缓存（page cache）自动管理——访问过的页保留（像热缓存），不访问的自动释放

### 什么时候用 `--no-mmap`？

**场景 1：你的 RAM 略小于模型大小，且频繁出现 pageout（页面换出）**

如果你只有 16 GB RAM，模型 14 GB，加上 KV 缓存和其他开销，系统可能频繁将部分模型权重换出到磁盘（swap），导致生成速度频繁卡顿。`--no-mmap` 强制全部权重始终驻留 RAM，避免这种"抖动"。

**场景 2：避免模型预热开销**

使用 mmap 时，模型权重是按需加载的。第一次推理时，每个权重的首次访问都会触发"缺页中断"（page fault），这会产生额外延迟。对于需要立即响应的生产环境，`--no-mmap` 确保全部权重在初始化时就加载完毕。

**场景 3：某些特殊硬件或虚拟机环境**

在某些虚拟化环境或特定 CPU 架构上，mmap 行为可能不稳定或性能较差，此时也需要 `--no-mmap`。

### 使用 `--no-mmap` 的代价

- **加载时间显著增加**（需要读取整个模型文件）
- **RAM 占用成倍增加**（模型同时占用 RAM 和 VRAM）
- **在 GPU 推理时反而可能浪费显存**（例如 Gemma-4B 用了 `--no-mmap` 反而比 9B 的 Qwen 更紧张）

> **建议**：对于纯 GPU 推理（`-ngl -1` 或大部分层在 GPU），**通常不需要 `--no-mmap`**。CPU+GPU 混合推理才需要考虑。

## `--mlock` 详解

### 什么是 mlock？

`mlock` 是 POSIX 系统调用（Windows 上通过 `VirtualLock` 实现），它告诉操作系统：**这段内存空间不许换出（swap），也不许压缩**。

### 什么时候用 `--mlock`？

**场景 1：系统 RAM 充足，但 OS 倾向于换出**

即使你有 64 GB RAM，Linux 仍可能将一些"看起来不活跃"的内存页换出到 swap，以释放给文件缓存。当 llama.cpp 再次访问这些页时，会触发一次 swap-in，导致延迟尖刺。`--mlock` 阻止这种行为。

**场景 2：低延迟实时应用**

如聊天机器人、语音助手等场景，任何一次卡顿（即使是几百毫秒的 swap-in）都会影响用户体验。

**场景 3：CPU 推理（非 GPU）**

CPU 推理时模型权重直接驻留在 RAM，`--mlock` 确保这些权重永远不会被换出，保证稳定的生成速度。

### 使用 `--mlock` 的代价

- 需要足够的可用 RAM（被锁定的内存无法用于其他程序）
- 在 Linux 上可能需要调整 `memlock` ulimit（默认通常很低，如 64 KB）

## 两者对比

| 维度 | `--no-mmap` | `--mlock` |
| ---------------- | --------------------------------- | -------------------------------------- |
| **机制** | 不使用内存映射，强制全部读入 RAM | 使用内存映射，但锁定已映射的内存不换出 |
| **加载速度** | 慢（全量读取） | 快（按需读取） |
| **RAM 占用** | 高（整个模型 + 副本） | 正常（mmap 管理的页面） |
| **运行时稳定性** | 保证全部在 RAM | 保证不 swap，但首次访问仍需 page fault |
| **适用场景** | RAM 勉强够用、需要避免 page fault | RAM 充裕、需要防止 swap 导致的卡顿 |
| **GPU 推理** | 一般不需要 | 一般不需要 |

---

## 如何选择

以 GPU 推理、模型种类较多的场景为例：

| 情况 | 建议 |
| ------------------------------------------------ | -------------------------------------------------------------------------------------------------------- |
| **纯 GPU 推理（`-ngl -1`）** | **两个都不需要**。模型权重在 VRAM 中，RAM 占用本来就不大 |
| **CPU+GPU 混合推理（部分层在 RAM）** | 用 `--mlock` 而不是 `--no-mmap`。加载快，运行时稳定，不浪费 RAM |
| **RAM 刚好够用（模型 + KV 缓存 ≈ 80%~90% RAM）** | 考虑 `--no-mmap`，避免频繁 pageout |
| **Gemma 模型（小参数量）** | 可以**去掉 `--no-mmap`**，因为模型小，GPU 推理时 mmap 完全够用 |
| **MoE 大模型（35B/26B，IQ2_M/Q4_0）** | 如果大部分层在 CPU（RAM），建议 `--mlock`；如果 CPU 卸载的只是少数 expert 层（`-ot exps=CPU`），可以不用 |

**简单规则**：

- 模型能全部塞进 GPU → **两个都不需要**
- 模型主要跑在 CPU 上 → **加上 `--mlock`**
- 模型大小接近 RAM 极限 → **加上 `--no-mmap`**
